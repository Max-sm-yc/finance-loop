# Power Automate setup for supplier receipt intake

This guide covers transferring the original supplier file into Finance Loop and checking its processing status. Teams and email triggers are choices for the flow owner; this document does not create or operate those flows. Power Automate only submits evidence and reads status. A person approves cost, stock, and payment effects in Finance Loop.

## Before building a flow

1. Deploy the Finance Loop release and apply its reviewed migrations in the intended Supabase project. Confirm the Render receipt worker is running and the web app has the same release.
2. In Finance Loop, have an owner create an integration credential for the target workspace. Copy the token at creation time into an approved secret store, such as Azure Key Vault or a protected Power Platform environment variable. The token is shown once. If lost, revoke it and issue a new one.
3. Record the Finance Loop base URL from the deployed environment, for example `https://operations.example.com`. Use the same environment for the credential, API, and worker.
4. Create a cloud flow with the chosen file source. Keep its connector connection restricted to the service identity that is authorized to read that mailbox or library.

## Flow outline

Use the cloud **HTTP** action (licensing and connector availability depend on your tenant). The HTTP with Microsoft Entra ID connector is a separate option and requires Entra authentication; this integration uses the bearer token generated by Finance Loop. Build the actions in this order:

1. **Get file content.** Retrieve the original attachment/document bytes, not a preview, sharing link, or base64 string embedded in JSON. Keep the original filename and content type. Finance Loop accepts PDF, JPEG, and PNG, up to 8 MiB per file and 20 PDF pages.
2. **Create stable identifiers.** Keep the source's opaque immutable identifier as `externalSubmissionId` if it is at most 200 characters and contains no control characters. Otherwise derive a bounded deterministic digest or look up a persisted stable mapping, and use that same mapped value on retries; do not silently truncate. Add a Compose action named `Stable_idempotency_key` for a separate deterministic key from source IDs, for example `concat('mail-', triggerOutputs()?['body/id'], '-', items('Apply_to_each')?['id'])`. The `Idempotency-Key` header has a safe-character rule and must be 8–200 characters: use letters, numbers, underscore, colon, period, slash, and hyphen. If source IDs exceed that or contain other characters, use a deterministic encoding or hash of the source identifiers; do not use a fresh `guid()` on every run. Both values must remain stable across retries and unique within the workspace. Avoid supplier or amount data in either identifier.
3. **Register the submission.** Send `POST {baseUrl}/api/integrations/purchase-receipts` with header `Authorization: Bearer <token>`, `Idempotency-Key: <outputs('Stable_idempotency_key')>`, `Content-Type: application/json`, and body:

   ```json
   {
     "externalSubmissionId": "<original-opaque-source-id>",
     "filename": "<original-filename>",
     "contentType": "application/pdf"
   }
   ```

   Save `receiptId`, `status`, and any returned `upload.url`, `upload.method`, `upload.contentType`, and `upload.headers`. Expressions for the HTTP action output are `body('Register_receipt')?['receiptId']` and `body('Register_receipt')?['upload']?['url']`. Reusing the same source ID and idempotency key after a timeout must return the same receipt. If the receipt has advanced past `awaiting_upload` and no upload destination is returned, skip upload and completion and poll its existing status.
4. **Upload the bytes.** When an upload destination is returned, send the returned HTTP method (`PUT`) to that URL. Use the returned `upload.contentType` and `upload.headers` exactly. The signed URL already includes its upload authorization, so do not forward the integration bearer token to the storage host. Set the body to the source connector's native **File Content** dynamic value. Some connectors expose a content object with `$content-type` and base64 `$content`; only for that connector shape, use `base64ToBinary(body('Get_file_content')?['$content'])`. Do not base64 encode an already-binary output or wrap bytes in JSON. Check the status code before continuing. If a retry reports that the object already exists, call `complete` to let Finance Loop verify the previous upload instead of creating another submission.
5. **Complete intake.** Send `POST` to `concat(variables('FinanceLoopBaseUrl'), '/api/integrations/purchase-receipts/', body('Register_receipt')?['receiptId'], '/complete')` with the bearer token, JSON content type, and body `{}`. Finance Loop verifies the stored object and queues processing. A `202 Accepted` response means queued for processing, not reviewed or posted. If registration showed the receipt was already queued or further along, skip completion and poll its current status.
6. **Poll status.** Use a `Do until` loop around `GET` to `concat(variables('FinanceLoopBaseUrl'), '/api/integrations/purchase-receipts/', body('Register_receipt')?['receiptId'])` with the bearer token. Use a `Delay` action of 30–60 seconds between requests and a finite loop count/timeout. Stop when a person can act or processing has finished; for example, a terminal-condition expression can be `@or(equals(body('Get_receipt_status')?['status'],'needs_review'),equals(body('Get_receipt_status')?['status'],'approved'),equals(body('Get_receipt_status')?['status'],'projection_pending'),equals(body('Get_receipt_status')?['status'],'posted'),equals(body('Get_receipt_status')?['status'],'duplicate'),equals(body('Get_receipt_status')?['status'],'rejected'),equals(body('Get_receipt_status')?['status'],'failed'))`. Handle HTTP `429`/`5xx` with bounded exponential retry; do not poll indefinitely.
7. **Route the outcome.** On `needs_review`, combine the base URL with the returned relative URL using `concat(variables('FinanceLoopBaseUrl'), body('Get_receipt_status')?['reviewUrl'])`; the link is shaped like `/?purchaseReceipt=<receiptId>&organizationId=<workspaceId>`. Pass it to the authorized reviewer using your normal internal process. On `duplicate`, review `duplicateOfReceiptId` and alert the flow owner or reviewer without submitting a second file. On `failed`, alert the flow owner with the receipt ID and safe status text. A failed terminal receipt does not automatically restart when the same ID is resubmitted; have the workspace owner investigate and use the supported recovery process after the cause is corrected. Do not automatically approve or post anything.

The signed URL already contains its upload authorization. Use its returned URL and content type exactly; do not construct a storage URL.

## Idempotency and recovery

- A Power Automate retry after an HTTP timeout must reuse the same `externalSubmissionId` and the same source file. The register endpoint is the idempotency boundary.
- If registration succeeded but its response was lost, call register again using that same ID to recover the existing receipt/upload details. If the receipt has moved to `queued` or later, continue by polling its status rather than uploading again.
- If the upload failed, retry its PUT using the same returned destination while valid. If the destination expired, call register with the same ID and follow the API's returned upload state; never silently create a second receipt.
- Call `complete` only after a successful upload. Calling it twice must not enqueue duplicate processing.
- Keep a flow run identifier only for diagnostics; do not use it instead of the stable source ID.

## Protect credentials and documents

- Do not place integration tokens in a literal action field, email, Teams message, document, or source control. Read secrets from Key Vault or a protected environment variable / connection value with tightly scoped access.
- Turn on **Secure inputs** and **Secure outputs** for every action that reads or sends the bearer token, upload URL/token, or document bytes. In the new designer these toggles are in the action's **Settings → Security**; in the classic designer use the action ellipsis → **Settings**. Secure outputs on the file-content action also prevents binary data appearing in run history. These settings hide values from run history but do not replace least-privilege access to the flow.
- Restrict who can edit the flow, connection references, environment variables, and run history. Avoid logging request/response bodies that contain tokens or signed upload URLs.
- Use TLS endpoints and do not forward Finance Loop credentials to a Teams/email requester. Revoke and rotate the integration credential immediately if exposed.
- Treat receipt content as untrusted data. The worker extracts evidence for human review; instructions printed inside a document never authorize actions.
